## Level 1 — Plain English Machine

A Greenhouse board token is an address label for a source of job listings.
An employer is the business we intentionally identify. One business may have
multiple boards; a changed display name does not necessarily mean a new business.
Similar names do not prove that two businesses are the same.

A canonical employer ID is our stable internal key, such as emp-rocket-lab.
The employer registry explicitly connects that key, the display name and board
tokens. Think of a vendor master: a vendor number is different from the vendor's
printed name and the addresses used to receive its documents. We do not merge
vendors because their names look alike.

The four existing sources remain technical pilots. ACTIVE means configured for
normal searches; BENCH means kept for later selection; PAUSED means not searched.
Nothing automatically promotes or demotes an employer. A report showing four
ACTIVE employers is truthful, not an error requiring six invented additions.

SQLite remembers operational facts after the program exits. A schema describes
its tables and columns. Schema version 2 tells the program which layout to expect;
the original jobs-only layout is recognized as version 1 even when its old numeric
marker is zero. Version numbers are not Job Scout release numbers.

A migration changes the layout while preserving existing records. Here it adds
employer identity and supporting tables without resetting APPLIED or altering
stored timestamps/snapshots. Unknown source identity stops migration. It does not
make up application dates or rewrite historical company names.

We rehearse migrations using invented records in temporary databases. A transaction
makes the migration all-or-nothing. Rollback means undoing the unfinished changes,
including the schema/version changes. The tests intentionally cause failures
after work has begun and confirm the old database bytes are unchanged.
This resembles a controlled conversion of an accounting register, reconciled back
to the original records before authorizing any production conversion.

Source-run observations record what we actually saw: which board was attempted,
when, whether retrieval succeeded, how many postings returned and how many unique
roles today's rules recognized. A successful search with zero relevant jobs is
evidence of zero for that observation. A failed search is unknown, recorded as
NULL counts. Treating failure as zero would distort later employer-yield analysis.
No observations were fabricated for the past.

Today Scout still filters/ranks and returns up to five jobs. Applying to one job
still affects only that job. Employer suppression, full application portfolio and
Excel export are later features, not hidden parts of this task.

## Level 3 — Code Literacy

Recognize patterns in the actual implementation before trying to write them.

From employers.json:

```json
"employer_id": "emp-rocket-lab",
"display_name": "Rocket Lab",
"greenhouse_boards": ["rocketlab"],
"approval_status": "PILOT",
"approval_date": null,
"pool": "ACTIVE"
```

Named fields form an object; the square brackets hold a list of explicit board
mappings. null means unknown, not zero or an invented approval date. Configuration
is data: nothing here becomes a shell command.

From employer_registry.py:

```python
return {board: employer for employer in registry["employers"]
        for board in employer["greenhouse_boards"]}
```

This dictionary comprehension builds a board-to-employer lookup after validation.
The two for clauses walk employers and their explicitly listed boards. It does not
search company names or infer ownership.

From application_state.py:

```python
connection.execute("PRAGMA foreign_keys=ON")
connection.execute("BEGIN IMMEDIATE")
version = connection.execute("PRAGMA user_version").fetchone()[0]
```

PRAGMA is SQLite's configuration/metadata syntax. Foreign keys enforce links
between rows. BEGIN IMMEDIATE starts a transaction and reserves the write lock.
fetchone returns a row; [0] reads its first value, the schema version.

The jobs table uses:

```sql
FOREIGN KEY (source_board, employer_id)
    REFERENCES employer_sources(board, employer_id)
```

A primary key identifies a row. This foreign key requires the job's board/employer
pair to exist in the source mapping, like a detail record pointing to a valid
master record. Explicit mappings preserve identity across display-name changes.

The unchanged mark operation retains parameterized SQL:

```python
"UPDATE jobs SET status=?, status_updated_at=? WHERE id=?"
```

Question marks are placeholders. Values are supplied separately, so a quoted
employer name or job ID cannot become SQL instructions.

The migration connection uses try/except:

```python
except Exception:
    connection.rollback()
    connection.close()
    raise
```

On failure, undo the transaction, release the connection and report the problem.
Do not delete the database and pretend the run succeeded.

From the rollback tests:

```python
self.assertEqual(self.db.read_bytes(), before)
```

An assertion compares the synthetic database after an intentional failure with
its original bytes. Passing tests support this tested behavior; they do not
authorize migration of Adam's real data.

Repeated vocabulary: def defines a function; return gives a result back; if checks
a condition; for repeats; import reuses code; JSON is structured data; SQLite is
persistent storage; CLI flags choose an action; Git versions code/docs, not ignored
private databases.
