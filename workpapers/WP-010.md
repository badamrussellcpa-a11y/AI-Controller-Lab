## Level 1 — Plain English Machine

Seeing a job is not applying. Shortlisting is not applying. A job is a discovered
opportunity; an application is an explicitly recorded fact about something you did.
Scout records that fact locally. It never submits an application or contacts anyone.

The machine now has two views of the same population:

- Complete discovery: keep all recognized opportunities visible, with factual labels.
- Application selection: exclude handled jobs, incompatible locations and restricted
  employers unless a valid job-specific override authorizes consideration.

Company A → Senior Accountant application recorded → employer selection suppressed
→ new Controller appears → Controller stays visible and NEW → active-application
warning → Adam reviews context → optional explicit Controller-only authorization.

The application has its own ID and event history. Its job becomes APPLIED, but its
sibling jobs do not. APPLIED, SCREEN, INTERVIEW and an unresolved OFFER are active.
Employer pool ACTIVE/BENCH/PAUSED is a different dimension and never changes here.

The two rejection paths matter:

| Recorded facts | Employer consequence, if no other restriction exists |
| --- | --- |
| Applied; rejected; explicitly confirmed no meaningful engagement | Eligible again |
| Applied; recruiter screen/interview; rejected or withdrawn | REVIEW BEFORE REAPPLYING |
| Closed; engagement unknown | Review required; unknown is not No |
| Unresolved offer | Active application; sibling selection suppressed |

A prior YES remains historical truth. A prior NO does not prove nothing happened
later: a rejection with unknown subsequent interaction still needs review. Dates
you do not know stay null. Recording time means when the system saved a fact, not
when an application or interview happened.

An override is permission to consider one named opportunity under known restrictions.
It is not an application, a changed sibling label or permanent company-wide permission.
It has a reason and timestamp. No timer expires it. New application/closure/review
facts or changed listing content require fresh authorization; old decisions remain
inspectable. Resolving review is another explicit decision; it cannot erase another
active application or unreconciled legacy evidence.

Legacy APPLIED/INTERVIEW/OFFER/REJECTED labels are retained exactly during migration.
They do not contain sufficient history to infer dates, engagement or rejection timing.
The employer waits for explicit reconciliation: current eligibility, reapply review,
or linking to an independently recorded application. Old labels and decisions remain.

CPA analogy: a current account balance is not a transaction journal. The jobs table
is a current-state register; application events preserve the supporting entries.
Do not manufacture missing entries merely to make the register easier to reconcile.
An explicit human disposition documents the decision without inventing historical facts.

The trace is: application fact → approved business rule → derived employer restriction
→ selection exclusion → named exception/override → retained evidence. A successful
program run is not proof that a human-supplied fact was correct.

## Level 3 — Code Literacy

Real table fields:

```sql
application_id INTEGER NOT NULL REFERENCES applications(application_id),
engagement TEXT NOT NULL CHECK (engagement IN ('UNKNOWN', 'NO', 'YES')),
occurred_at TEXT,
recorded_at TEXT NOT NULL
```

REFERENCES is a foreign key: an event must belong to a real application record.
CHECK limits the permitted values. Nullable occurred_at preserves unknowns; required
recorded_at gives the audit-entry time. NULL is not zero, No or an invented date.

The actual engagement derivation:

```python
values = [e["engagement"] for e in app["events"]]
app["engagement"] = "YES" if "YES" in values else values[-1]
```

A list comprehension visits each event dictionary. The conditional expression
preserves any historical YES; otherwise it uses the latest recorded knowledge.
The last element is values[-1]. Functions package a calculation and return its
result. In _relationships, if the stage is active it creates an active restriction;
elif a closed application's engagement is not NO, it creates reapply review.
Those restrictions are derived values, not employer flags manually kept in sync.

Writes use placeholders:

```python
connection.execute("UPDATE jobs SET status='APPLIED', status_updated_at=? WHERE id=?", (now, job_id))
```

The SQL structure is fixed. Values go through parameters, so text is data rather
than instructions. BEGIN IMMEDIATE and the connection context keep related inserts
and updates in one transaction: either all succeed or rollback preserves prior facts.
Migration likewise includes table changes, copied legacy evidence and schema version
in one transaction. Tests inject a failure after changes to prove rollback.

The selection rule includes:

```python
job["selection_eligible"] = (allowed and statuses[job["id"]] in FRESH_STATES
                             and job["location_classification"] != "INCOMPATIBLE")
```

Each condition must be true. allowed comes from the employer relationship/override.
This marks selection eligibility; it does not remove the job from complete discovery.
An override stores the restriction's fact IDs and the authorized listing snapshot.
Comparing that saved context to current facts detects change; the original evidence
remains readable in history. Storage is not proof that human-supplied facts are true.

From the acceptance tests:

```python
self.assertEqual(len(run["jobs"]), 7)
self.assertEqual(run["selection_job_ids"], [])
```

Seven visible jobs and zero selectable jobs can both be correct while an employer
has an active application. Other assertions verify the sibling remains NEW, a
specific override exposes only that sibling, and both facts/history survive restart.
