## Level 1 — Plain English Machine

Today's Scout reads four public Greenhouse employer feeds, recognizes selected
accounting roles, gathers keyword evidence, remembers job states in local SQLite,
and writes up to five eligible jobs as Markdown and JSON. Marking a saved job
APPLIED changes a local record; it does not submit an application. A later run
excludes that job while retaining its record.

The approved future machine is broader: a controlled employer pool, all broadly
relevant opportunities, separate employer suppression, factual application
portfolio and optional Excel analysis. Those are specifications, not functioning
features yet. Adam + ChatGPT will judge fit using real career evidence; Scout
will supply facts. Adam controls external applications and communications.

CPA analogy: today's SQLite table resembles a register containing the latest
balance/status, not a complete transaction journal. A future application history
must preserve prior events even when a job is reopened. The planned workbook is
an analysis extract, not the authoritative ledger.

Documentation reconciliation is like reconciling a workpaper to the actual
ledger: the description must agree with the system that exists. A release
acceptance checklist is not satisfied merely because a daily checkpoint passed.

## Level 3 — Code Literacy

Recognize before trying to rewrite. These excerpts come from current code;
this task changed no Python.

From application_state.py:

```python
FRESH_STATES = {"NEW", "SHORTLISTED"}
```

Braces here create a set of allowed fresh states. APPLIED is absent, so it does
not qualify for a fresh recommendation. This is a deterministic rule, not AI
judgment. Job state and future employer suppression are different controls.

From job_scout.py:

```python
statuses = record_jobs(args.state_file, candidates)
```

A function call asks the persistence component to save candidates and returns a
mapping of IDs to states. The variable on the left receives that result. Later
selection uses those states before applying the current result limit.

From application_state.py:

```python
"UPDATE jobs SET status=?, status_updated_at=? WHERE id=?"
```

The question marks are SQL parameter placeholders; values are supplied separately.
An ID is data rather than executable SQL. Updating one ID does not truthfully
mean every job at that employer was applied to.

Repeated recognition vocabulary:

| Pattern | Meaning in this project |
| --- | --- |
| def / return | Define a reusable operation / give its result back |
| for / if | Repeat over records / apply a condition |
| dictionary / list | Named fields or an ID mapping / a sequence of jobs |
| import | Reuse another module's functions |
| CLI | Typed options such as --mark and --history |
| SQLite | Local persistent operational records, included with Python |
| JSON | Structured report/listing data; not instructions |
| tests | Repeatable examples checking behavior, not proof of every live condition |
| Git | Versioned code/docs; not backup for ignored private databases |
| validation / encoding | Reject unsafe input / represent allowed input safely at output |

search_rules.md looks like documentation but is also parsed by Python. Its
weights, reject section and commute JSON must remain equivalent after wording
edits. A Markdown-only diff does not by itself prove unchanged behavior.
