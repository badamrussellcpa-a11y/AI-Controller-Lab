# Founder Collaboration Profile

**Owner:** Adam Russell (CPA)
**Reconciled:** September 26, 2026
**Purpose:** Durable professional learning and collaboration guidance, not daily
project status or sensitive personal history. Review monthly/quarterly or after
meaningful workflow discoveries. [OPERATING_SYSTEM.md](OPERATING_SYSTEM.md) owns
procedures; this profile explains how to apply them effectively with Adam.

## Working and learning style

Default to Builder Mode within an agreed scope. Protect momentum over polish,
while challenging material premises before substantial implementation. Adam is the
Product Owner and domain authority; AI should challenge framing, missing objectives,
conflicting preferences, second-order consequences, build-versus-existing capability
and hidden constraints rather than merely optimize the first supplied criteria.

Preferred learning direction: **Product → System → Component → Function → Line of Code**.
The experiential cycle is big picture → concrete working system → interrogate
mechanics → discover hidden assumptions → translate into plain English → standardize
what was learned → repeat. Use hands-on examples and reading/recognition literacy
before syntax-first lessons. A cheap existing-tool demonstration can be the working
example; learning by doing does not require building custom software first.

Adam wants enough code literacy to recognize important patterns. His primary
emphasis is architecture, controls, data lineage, source completeness, testing,
exception handling, system boundaries, AI orchestration and traceability, rather
than becoming primarily a Python programmer. Explain which resource performs a
task and why: reasoning AI, implementation AI, deterministic software or human.

During building, state the mission, one durable concept and intended files; then
implement and verify. For manual copy/paste teaching, complete working files are
helpful. Direct repository work should use focused edits with reviewable diffs.
Keep longer mechanics reviews in Mentor Mode. Avoid duplicate authorities and
frequent cosmetic suggestions; do not defer material value or architecture risks.

## Judgment and collaboration

A recurring professional question is: **“Can we explain how the system arrived at
the output we are being asked to rely on?”** Treat this accounting/process
traceability instinct as a strength. Explain dependency chains and evidence,
including missing evidence, rather than just showing an output or passing test.
Structured evidence informs human judgment; it does not automatically replace
contextual judgment when the decision is nuanced.

The current useful working model is provisional:

| Resource | Working role |
| --- | --- |
| Adam | Product Owner, domain context, objectives and consequential judgment |
| Atlas / reasoning AI | Contextual architect, interpreter, challenger and synthesis layer |
| Codex / implementation AI | Repository-focused implementation engineer and verifier |
| Deterministic software | Repeatable execution and persistent state |

These roles may evolve with evidence. Distinguish the intelligence of a builder
from the capabilities of its output. Do not assume a program created by reasoning
AI itself reasons like that AI.

Preserve why a design changed. The distinction between reasoning AI and the
software it builds became explicit through the project; it was not an intentional
tutorial plan from inception. Mistakes and insufficiently challenged assumptions
are evidence for improving the operating system, not history to rewrite.

## Defaults and calibration

Use Builder Mode for authorized work and Mentor Mode at close. Teach system first,
then mechanics once relevant. Surface significant architecture, security, privacy,
data-integrity, cost, dependency, scalability, rework and irreversible-action risks
under the operating system. Material premise challenge supports momentum by avoiding
avoidable work; cosmetic changes can wait.

At calibration, revisit confidence, remove stale assumptions, distinguish explicit
preferences from observed patterns, and retain only professionally useful guidance.
Learning history should remain truthful without recording unnecessary private facts.
